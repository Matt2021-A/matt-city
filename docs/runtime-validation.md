## Known operational issue

### Session snapshot and store-status latency

`gc status` has repeatedly timed out while loading the session snapshot after three seconds, then continued with runtime-only status. One isolated status run took more than 30 seconds.

The supervisor HTTP API itself responded quickly during the same investigation. The slow path therefore appears related to session projection, store reads, or concurrent maintenance activity rather than general API unavailability.

The runtime also showed sustained Dolt and Beads activity from order, wisp, convoy, query, and metrics processes. This remains an operational warning for later diagnosis. It is not the immediate Phase 1 gate.

Do not treat fallback agent counts from a timed-out status snapshot as authoritative without corroborating session evidence.

## Generated repository artifacts

Rig registration and runtime execution create local projections and state:

- `.beads/`
- `.agents/skills/`
- `.gc/`
- runtime worktrees, temporary prompts, and session files when active

Policy:

- runtime state remains local unless a specific artifact is approved for version control
- generated Gas City skills are not vendored by default
- hand-authored Matt City agent definitions remain under `city/agents/`
- request packages and approved workflow artifacts may be committed under `requests/`
- telemetry data will not be committed as a substitute for canonical Asana, Git, or Beads/Dolt state

## Remaining Phase 1 gates

- create a fresh request ID and workflow root
- route claimable work to the intended run target
- observe a concrete session claim the work
- execute the specialist steps with correct dependency ordering
- verify retry and finalization behavior
- capture real workflow, Bead, event, agent, and session identifiers together
- test session replacement without loss of durable work state
- produce a provenance record linked to the originating Asana task
- package artifacts in a Git-versionable path
- return results to the originating Asana task through the authorized assistant identity
- confirm no specialist agent performs external writes

A new smoke test must use a new workflow ID. Historical FileStore-era or earlier smoke-test IDs must not be reused as proof of the bd-backed lifecycle.

## Phoenix sequencing

Phoenix is committed but does not precede the current gate.

Sequence:

1. complete or stabilize the bd-backed workflow baseline
2. record the Phoenix architecture decision and privacy-safe telemetry policy
3. define the trace and correlation schema
4. instrument one fresh workflow with metadata-first spans
5. demonstrate that Phoenix loss cannot interrupt execution
6. add deterministic evaluations before LLM-judge evaluations
7. operationalize retention, access, health, and documentation

## Source-of-truth rule

Asana remains the canonical human work, decision, and approval plane. Gas City plus Beads/Dolt are the machine execution and durable-state plane. GitHub stores versioned implementation and approved artifacts. OpenTelemetry/Grafana own operational metrics and logs. Phoenix will own AI traces and evaluations. None of these systems should silently absorb another system's authority.
